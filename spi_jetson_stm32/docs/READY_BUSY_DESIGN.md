# READY/BUSY 握手重新设计

状态：设计稿；本版不选择任何实际物理管脚，也不改变当前默认通信行为。

## 设计目标

在不改变现有两次 SPI 操作和帧格式的前提下，增加一个可选的从机状态通知。通知只表达从机是否可以接受下一次事务：

| 电平 | 含义 |
|---|---|
| 高 | READY/IDLE：从机已完成上一请求并准备好下一次写事务 |
| 低 | BUSY：从机正在接收、解析、执行或准备响应 |

这是一个单向信号：STM32 驱动，Jetson 采样。它不是 SPI 数据，也不替代 CS；CS 仍然是每次事务的边界。

## 为什么不在本版指定管脚

目前代码只确认了 MCU 型号系列和 SPI 所需 PA4/PA5/PA6/PA7，尚未取得本次实际 STM32 扩展板的版本原理图、排针编号和已装模块清单；Jetson 载板的 40 针 pinmux 也可能由 JetPack 配置改变。任何直接写入的 `PAx/PBx`、40 针编号或 Linux GPIO offset 都可能与板上外设、跳线或当前 SPI 配置冲突。

因此本设计把“握手语义”和“板级引脚映射”分开：确认两端原理图和实测空闲状态后，新增一份板级配置，才允许打开握手功能。

## 时序

1. STM32 复位、初始化或 DMA 异常时保持 BUSY（低）。
2. SPI 从机接收已重新装载、没有待处理请求时置 READY（高）。
3. Jetson 发起写事务前，必须观察 READY；CS 拉低后 STM32 立即置 BUSY。
4. CS 上升沿中断只保存 DMA 快照并保持 BUSY；后台完成校验、回调和响应 DMA 准备后置 READY。
5. Jetson 观察到 READY 后发起读事务；读事务期间再次置 BUSY，读 CS 上升沿后恢复接收并在确认状态后置 READY。
6. READY 等待必须带超时；超时只报告通信未就绪，不自动重发可能已经执行的写命令。

READY 的状态变化应在对应 SPI CS 边沿之外完成建立时间；Jetson 不得把一次事务前残留的高电平当作本次命令已经完成。实现时应在发起写事务前清空/记录 GPIO 边沿事件，按“低→高”完成周期确认，或使用等价的序号/状态机制。

## 软件边界

- 共享协议层不读取或生成 READY/BUSY 字节，帧格式保持不变。
- STM32 SPI 驱动只调用抽象接口 `ready_set(BUSY/READY)`；接口由板级适配层实现。
- Jetson 主机把握手作为可选配置；未提供板级映射时保持现有 10 ms 兼容等待，不访问任意 GPIO。
- 板级配置至少包含：STM32 端 GPIO 端口/编号和复位默认状态、Jetson 物理排针号、Linux GPIO chip/line、pinmux 状态、电平标准、外部上下拉及是否与其他外设复用。

## 启用前验收

必须先提交实际两端资料和测量记录：

- STM32 开发板完整型号/版本、原理图中该信号的连接网络、排针针脚和已装模块；
- Jetson 载板型号、40 针连接器针号、Jetson-IO 当前功能和 `gpioinfo` 的占用状态；
- 两端均为 3.3 V、无反向驱动；复位、掉电和拔线时不会把 Jetson 输入误判为 READY；
- 示波器/逻辑分析仪确认 CS 与 READY 的先后关系、响应准备时间和超时行为。

在这些证据齐全前，代码不得把某个候选管脚标记为默认握手管脚。
